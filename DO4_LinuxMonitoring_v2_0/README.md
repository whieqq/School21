# DO4_LinuxMonitoring_v2_0 - мониторинг системы

Учебный проект DevOps-трека Школы 21. Полный цикл мониторинга: от скриптов, создающих нагрузку на файловую систему, до дашбордов Grafana и собственного экспортёра метрик для Prometheus.

Сдан на 143% - выполнено дополнительное задание.

## Структура

```
src/01/   - генератор файловой структуры по параметрам
src/02/   - засорение файловой системы в случайных местах
src/03/   - очистка файловой системы, три стратегии
src/04/   - генератор логов nginx
src/05/   - анализ логов на awk
src/06/   - анализ тех же логов через GoAccess (отчёт + готовые логи и HTML-отчёты)
src/07/   - Prometheus и Grafana, свой дашборд (отчёт)
src/08/   - готовый дашборд Node Exporter, нагрузочные тесты (отчёт)
src/09/   - собственный экспортёр метрик на bash (код + отчёт)
```

В частях 6-9 лежат отдельные README с ходом работы и скриншотами.

## 1. Генератор файловой структуры

Принимает шесть параметров: путь, количество вложенных папок, буквы для имён папок, количество файлов в каждой папке, буквы для имён файлов с расширением, размер файлов.

```bash
./main.sh /opt/test 4 az 5 az.az 3kb
```

Имена собираются из заданных букв и даты запуска, ведётся лог-файл. Главная защита: генерация останавливается, когда на диске остаётся меньше 1 ГБ свободного места, - иначе скрипт забьёт раздел полностью.

Код разбит на модули: разбор и проверка аргументов, работа с логом, контроль свободного места, создание файлов, сборка имён.

## 2. Засорение файловой системы

Имитация аварийной ситуации: папки создаются в случайных местах файловой системы, количество файлов в каждой тоже случайное. Каталоги с системными бинарниками (`bin`, `sbin`) исключены.

```bash
./main.sh az az.az 3Mb
```

Ведётся лог со временем начала, окончания и длительностью работы. Та же защита по свободному месту.

## 3. Очистка файловой системы

Удаляет созданное тремя способами - параметр выбирает стратегию:

```bash
./main.sh 1   # по лог-файлу
./main.sh 2   # по дате и времени создания, с точностью до минуты
./main.sh 3   # по маске имени (символы_дата)
```

Разные стратегии нужны на разные случаи: лог-файл может быть потерян, тогда остаётся ориентироваться на время создания или на шаблон имени.

## 4. Генератор логов nginx

Создаёт пять файлов логов, по одному на день, от 100 до 1000 записей в каждом. Случайно выбираются IP, метод (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), код ответа, URL и user-agent. Даты в пределах файла идут по возрастанию.

Все используемые коды ответа расшифрованы комментариями в коде: от `200 OK` и `201 Created` до `502 Bad Gateway` и `503 Service Unavailable`.

Готовые логи лежат в `src/06/nginx_logs/` - 2166 записей за пять дней.

## 5. Анализ логов на awk

Четыре режима выборки, параметр задаёт режим:

```bash
./main.sh 1   # все записи, отсортированные по коду ответа
./main.sh 2   # уникальные IP
./main.sh 3   # запросы, завершившиеся ошибкой (4xx и 5xx)
./main.sh 4   # уникальные IP среди ошибочных запросов
```

## 6. Тот же анализ через GoAccess

Те же четыре выборки, но инструментом готового анализатора логов. Отдельно показан веб-интерфейс: отчёт генерируется на виртуальной машине, поднимается простой веб-сервер, локальный порт пробрасывается через SSH-туннель, и отчёт открывается уже на основной машине.

Сгенерированные отчёты сохранены: `src/06/report.html` и `src/06/report_errors.html`.

## 7. Prometheus и Grafana

Установка обоих сервисов на виртуальной машине, доступ к веб-интерфейсам с локальной машины через проброс портов 9090 и 3000 по SSH.

Собран собственный дашборд с четырьмя показателями: загрузка процессора, доступная оперативная память, свободное место на диске и количество операций ввода-вывода.

Проверка на реальной нагрузке: сначала запускается скрипт засорения файловой системы из части 2 (видна нагрузка на диск), затем стресс-тест утилитой `stress`. Первый прогон почти не дал картинки - у машины 8 ГБ памяти и 4 процессора, поэтому параметры теста были увеличены до `stress -c 4 -i 2 -m 2 --vm-bytes 512M -t 60s`, а окно времени в Grafana сужено.

## 8. Готовый дашборд Node Exporter

Импорт дашборда Node Exporter Quickstart and Dashboard из каталога Grafana Labs и прогон тех же тестов на нём для сравнения с собственным дашбордом.

Дополнительно - нагрузочный тест сети между двумя виртуальными машинами через `iperf3` в пять параллельных потоков.

## 9. Собственный экспортёр метрик

Экспортёр на bash (`src/09/my_node_exporter.sh`), отдающий метрики в формате Prometheus через nginx. Оформлен как служба systemd с автозапуском, Prometheus переключён на него отдельным job в конфигурации.

Отдаёт пять метрик с корректными блоками `# HELP` и `# TYPE`: загрузка процессора в процентах, всего и доступно оперативной памяти, размер и свободное место на корневой файловой системе.

Что внутри стоит отметить:

- **Загрузка процессора считается по дельтам `/proc/stat`**, а не разовым снимком. Скрипт хранит предыдущие значения total и idle, и на каждом цикле вычисляет долю занятого времени за интервал. Разовое чтение `/proc/stat` даёт среднее с момента загрузки системы и для мониторинга бесполезно.
- **Запись атомарная**: файл сначала пишется во временный, затем переносится через `mv`. Без этого Prometheus периодически читал бы наполовину записанный файл и падал на разборе.
- **Интервал обновления** - 3 секунды, в соответствии с условием.

## Результат

Основной навык проекта - понимать мониторинг не как установку готовых дашбордов, а как цепочку «источник метрики -> экспортёр -> сбор -> визуализация», и уметь встроить в неё собственный источник.
